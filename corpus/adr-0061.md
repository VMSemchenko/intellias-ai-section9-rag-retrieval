# ADR-0061: Outbound connection pool sizing for checkout

**Status:** Active.

## Context

After `checkout-svc` migrated to the v4 token exchange described in ADR-0042, the
service began exhausting its outbound HTTP connection pool under ordinary afternoon
load. The symptom that reached customers was the edge returning an error page; the cause
was three layers down.

The v4 migration added one outbound request per token lifetime that did not exist under
v3, where identity arrived in a cookie and was introspected with a call that our client
library pooled separately. Nobody re-sized the pool. The default `httpx` limit of 10
keepalive connections was inherited from a service that made almost no outbound calls.

Under load the pool saturated. New requests queued waiting for a free connection, and
once the queue wait exceeded the client timeout they failed with `PoolTimeout`. Because
the failure happened while acquiring a connection rather than during the request, the
retry logic treated it as a transport error and retried immediately, which made the
saturation worse.

The edge maps an unhandled upstream failure or a request that exceeds the route deadline
onto a generic upstream gateway error. So a connection pool that was two sizes too small
surfaced to users as an edge error with nothing in `checkout-svc`'s own error logs.

## Decision

Outbound pools are sized from measured concurrency, not from library defaults.

    limits = httpx.Limits(
        max_connections=200,
        max_keepalive_connections=100,
        keepalive_expiry=30.0,
    )
    timeout = httpx.Timeout(connect=1.0, read=3.0, write=3.0, pool=0.5)

Three rules follow from this incident:

1. `pool` timeout must be **short** and distinct from `read`. A long pool wait converts
   a capacity problem into a latency problem and hides it.
2. `PoolTimeout` is a saturation signal, not a transport error. It must not be retried.
   Retrying a pool timeout is a positive feedback loop.
3. Every service that migrates to v4 token exchange re-derives its pool size before the
   migration, not after.

## Consequences

Pool exhaustion is now visible as a distinct failure mode instead of an opaque edge
error. The triage path for the customer-visible symptom is in the checkout runbook.
