# ADR-0080: Replace webhook fan-out with a shared event broker

**Status: DRAFT.** Not accepted. Do not build against this. Do not treat ADR-0038 as
deprecated on the strength of this document — the deprecation register is the authority on
what is deprecated.

## Problem

`notify-svc` fans out every event by making one outbound HTTP request per subscription.
With 41 active subscriptions a single `order.captured` becomes 41 outbound requests, each
with its own retry schedule and its own failure mode. Three consequences:

- Delivery latency for the last subscription is bounded by the per-destination concurrency
  cap, not by the destination's own speed.
- The retry state machine is duplicated per subscription and is the largest source of
  complexity in the service.
- Internal consumers pay the cost of an HTTP round trip to receive an event that was
  already inside our network.

## Proposal

Split internal and external delivery.

Internal consumers subscribe to a broker topic. `notify-svc` publishes once. Ordering and
replay become the broker's problem rather than ours, and internal consumers stop needing
an HTTPS endpoint.

External partners keep webhooks, delivered by a thin worker that consumes the same topic.
The retry schedule from ADR-0055 still applies to that last hop.

## Open questions

1. Which broker. Kafka is already operated for the analytics pipeline; whether that
   cluster should carry transactional events is unresolved.
2. Migration path for the 12 internal consumers currently on webhooks.
3. Whether per-subscription ordering survives. ADR-0038 promises ordering per
   subscription; a shared topic gives ordering per partition. These are not the same
   promise and the difference is user-visible.
4. Signature compatibility for partners during the transition.

## Why this is still a draft

Question 3 is a change to a published guarantee. Until there is a concrete answer that
does not silently weaken it, this ADR is not ready to be accepted.
