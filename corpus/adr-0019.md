# ADR-0019: Edge routing, deadlines and upstream error mapping

**Status:** Active.

## Context

Every external request enters through one gateway. It needs a single, predictable policy
for how long a request may take and what the client sees when something upstream fails.

## Decision

### Deadlines

Each route declares a deadline. The gateway cancels the upstream request when it expires;
it does not wait for the upstream's own timeout.

| Route class | Deadline |
|---|---|
| Read (catalog, order status) | 2 s |
| Write (order submission) | 8 s |
| Bulk export | 60 s |
| Auth token exchange | 3 s |

A route with no declared deadline inherits 2 s. This has surprised teams shipping a slow
write endpoint, which is the intended behaviour.

### Error mapping

The client never sees an upstream's internal error shape. The gateway maps:

| Upstream condition | Client sees |
|---|---|
| Connection refused, reset, or DNS failure | `502` |
| No response before the route deadline | `504` |
| Upstream returned `5xx` | passed through, `upstream_status` recorded |
| Upstream returned an unparseable response | `502` |
| No healthy upstream instances | `503` with `Retry-After` |

This mapping is why a service can look healthy in its own dashboards while users see
errors: a connection that never reached a handler produces a gateway `502` with no
corresponding entry in the upstream's request log. The `upstream_status` field in the edge
access log distinguishes the two cases and is the first thing to check during 5xx triage.

## Consequences

Deadlines are enforced at exactly one place, so a slow dependency cannot hold a client
connection open indefinitely.

The cost is that the gateway will cancel a request the upstream would eventually have
completed. For writes this means the client does not know whether the write happened —
which is why write endpoints require idempotency keys (ADR-0048).
