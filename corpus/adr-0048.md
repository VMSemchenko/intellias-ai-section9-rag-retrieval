# ADR-0048: Idempotency keys for order submission

**Status:** Active.

## Context

`POST /orders` is not naturally idempotent: two identical requests create two orders and
charge the customer twice. Under the ADR-0055 retry budget a client may legitimately
retry a request whose response was lost, so duplicates are not a hypothetical.

## Decision

`POST /orders` requires an `Idempotency-Key` header. The client generates it, typically a
UUIDv7, and reuses the same value for every retry of the same logical submission.

`checkout-svc` stores `(tenant_id, idempotency_key)` with the request fingerprint and the
serialised response, for 24 hours.

- Unknown key → process the order, store the response, return it.
- Known key, matching fingerprint → return the stored response with
  `Idempotent-Replay: true`. Do not reprocess.
- Known key, **different** fingerprint → `422`. The client reused a key for a different
  payload, which is a client bug we refuse to guess about.
- Known key, original request still in flight → `409`, `Retry-After: 1`.

Requests without the header are rejected with `400`. There is no grace period; a missing
key is the failure mode this ADR exists to prevent.

## Consequences

The 24-hour window is a storage cost we accept. It matches the outer edge of the
asynchronous retry schedule in ADR-0055, so a retry that arrives a day late still
deduplicates.

The `409` in-flight case means clients must tolerate being told to wait. Clients that
treat `409` as terminal will surface a spurious error to the user.

Idempotency keys do not make the *downstream* ledger write idempotent. That is handled
separately by the ledger's own entry deduplication.
