# ADR-0075: Naming conventions for metrics and log fields

**Status:** Active. This ADR covers naming only. Which signals to collect, how to alert on
them and how to trace a request are not decided here.

## Context

Four services had four different names for the same idea — `http_reqs`, `requests_total`,
`req_count`, `handled`. Cross-service dashboards were impossible without a translation
layer in every query.

## Decision

### Metrics

`{service}_{subject}_{unit}` with a `_total` suffix for counters.

    checkout_orders_submitted_total
    checkout_httpx_pool_pending
    auth_token_exchange_duration_seconds
    catalog_index_lag_seconds

Rules:

- Units in the name, always. `_seconds`, `_bytes`, `_minor` for currency. Never
  `_ms` — Prometheus convention is base units.
- Label cardinality below 100 per label. No user ids, no order ids, no full URL paths as
  labels. A high-cardinality label is the most reliable way to take down the metrics store.
- `route` labels use the templated form `/v4/orders/{order_id}`, never the concrete path.

### Log fields

Structured JSON, `snake_case`, and these keys are reserved with fixed meanings:

| Field | Meaning |
|---|---|
| `service` | emitting service |
| `route` | templated route |
| `status` | HTTP status returned to the caller |
| `upstream_status` | status the gateway received from upstream; empty when none |
| `trace_id` | propagated, never generated per log line |
| `tenant_id` | always present on request-scoped logs |

`upstream_status` is reserved because 5xx triage depends on distinguishing "upstream
returned an error" from "no usable response at all" — see ADR-0019 and the gateway triage
runbook.

## Consequences

Renaming existing metrics is a breaking change for dashboards and alerts. Migration is
per-service with both names emitted for one release.
