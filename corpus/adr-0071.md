# ADR-0071: Read-through cache for product detail

**Status:** Active. Also introduces the v2 response envelope that supersedes the v1
envelope from ADR-0022.

## Context

Product detail is the hottest read in the platform: roughly 60% of all catalog traffic, and
overwhelmingly for the same few thousand products. Serving each one from Postgres was
adding avoidable load to the primary and putting the p99 of the product page at 180 ms.

Search cannot serve this read: the index is asynchronous and may be up to 30 seconds stale
(ADR-0022), and a customer editing a product expects to see their own write immediately.

## Decision

A read-through cache in Redis, keyed `product:{tenant}:{sku}:{locale}`, TTL 300 seconds.

- Read: cache miss loads from Postgres, populates, returns. Concurrent misses for the same
  key are collapsed with a short lock so a cold popular key does not stampede.
- Write: the mutation path **deletes** the key rather than rewriting it. Writing the new
  value from the mutation path means two concurrent writers can leave the cache holding the
  older value permanently.
- Read-your-writes: a mutation returns a token the client sends on its next read, which
  forces a cache bypass for that request only.

## Consequences

p99 for product detail dropped to 22 ms and primary read load fell by roughly half.

Stale reads of up to 300 seconds are possible if a delete is lost — for instance if Redis
is unreachable at the moment of the mutation. The mutation does not fail in that case; it
logs and continues, because failing a customer's product edit because a cache is down is
the wrong trade. This means the cache is eventually consistent with a worst case of one
TTL.

Price is excluded from this cache. A stale price is a commercial problem rather than a
cosmetic one, so price is always read through to Postgres.
