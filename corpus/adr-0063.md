# ADR-0063: Rate limiting at the edge

**Status:** Active.

## Decision

Rate limiting happens at the gateway, not in each service. One implementation, one place to
reason about, one place to change during an incident.

Algorithm: sliding window counter in Redis, 10-second buckets, evaluated per key.

| Key | Limit | Applies to |
|---|---|---|
| Authenticated subject | 600 req/min | all routes |
| Authenticated subject, write routes | 60 req/min | `POST`, `PUT`, `DELETE` |
| Source IP, unauthenticated | 120 req/min | login, public catalog |
| Partner API key | per contract | negotiated, stored in config |
| Token exchange per device | 20 req/min | mirrors the auth-svc limit |

Exceeded limits return `429` with `Retry-After` and `X-RateLimit-Remaining`. Clients must
honour `Retry-After`; `429` is in the retryable set under ADR-0055.

## Fail open, deliberately

If Redis is unavailable the gateway **allows** the request and increments
`gateway_ratelimit_failopen_total`. A rate limiter that fails closed turns a Redis blip into
a full outage. We accept a window of unlimited traffic over that.

This is a considered trade-off, not an oversight. It means the rate limiter cannot be relied
on as a security control — it is a capacity control. Anything that must hold under Redis
failure belongs in the service, not here.

## Consequences

Services can assume they will not be flooded by a single caller under normal operation, but
must still shed load independently, because of the fail-open behaviour above.

The per-subject write limit of 60/min has been hit by legitimate bulk-import tooling twice.
Bulk operations use a partner API key with a negotiated limit rather than a user subject.
