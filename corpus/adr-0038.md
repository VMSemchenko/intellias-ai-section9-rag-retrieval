# ADR-0038: Webhook delivery guarantees

**Status:** Active. A replacement is drafted in ADR-0080 but not accepted.

## Context

Partners need to be told when an order changes state. Some partners have flaky endpoints,
maintenance windows and, in one case, an endpoint that returns `200` for requests it
silently discards.

## Decision

`notify-svc` guarantees **at-least-once** delivery, ordered per subscription but not
globally.

- Each event is persisted before any delivery attempt. Nothing is delivered from memory.
- Delivery is asynchronous. The producing service returns to its caller without waiting.
- Retries follow the asynchronous schedule in ADR-0055 — `notify-svc` does not define its
  own retry policy, and any per-destination override needs a written exception.
- A destination is considered failing after three consecutive terminal failures; further
  events for it are queued rather than attempted, and the subscription is marked degraded.
- Signatures cover the raw body. The signing subject is currently read from the v3 session
  record, which is the blocker on this service's v4 migration.

## What at-least-once means for consumers

Consumers **will** see duplicates. This is not a bug we intend to fix — exactly-once
delivery over an unreliable network is not available, and the honest answer is to make
consumers idempotent. Every event carries a stable `event_id`; deduplicate on it.

Ordering is per subscription and best-effort. A retried event can arrive after a newer
event for the same order. Consumers must use the `sequence` field rather than arrival
order, and must tolerate gaps caused by events still in retry.

## Consequences

The retry schedule spans 24 hours, so a partner down for an afternoon recovers with no
operator involvement. The cost is that a duplicate can arrive a day late, long after the
consumer's own request context is gone.

Terminal failures land in the dead-letter queue. Draining it is a manual procedure with
its own runbook.
